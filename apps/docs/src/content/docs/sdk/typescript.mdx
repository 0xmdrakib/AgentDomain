## Install

```bash
npm install @agentdomain/sdk@0.9.0 viem@2.56.3
```

The default API base is `https://api.agentdomain.app/api/v1` and the default network is Base
mainnet.

In SDK 0.9.0, relative `apiUrl` values are resolved against
the browser location at construction, before signing or payment. Non-browser clients must
provide an absolute URL. HTTPS is required except for explicitly configured HTTP loopback
hosts (`localhost`, `127.0.0.1`, or `[::1]`). API bases cannot contain credentials, a query,
or a fragment.

## Construct a client

```ts
import { AgentDomain } from '@agentdomain/sdk';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import type { PrivateKeyAccount } from 'viem/accounts';

export function createAgentDomain(account: PrivateKeyAccount) {
  const walletClient = createWalletClient({ account, chain: base, transport: http() });

  return new AgentDomain({ walletClient });
}
```

Supply the account through your wallet or secret-management integration. For agent-scoped server
operations, construct `AgentDomain` with an `apiKey` instead and keep that value server-side.

## Quote and register

```ts
const quote = await agentDomain.quote({
  preferredName: 'research-agent',
  tld: 'ai',
  registerBasename: false,
  registerEns: false,
  emailUsername: 'agent',
  years: 1,
});

const identity = await agentDomain.register({
  preferredName: 'research-agent',
  tld: 'ai',
  registerBasename: false,
  registerEns: false,
  emailUsername: 'agent',
  years: 1,
});

console.log(quote.totalUsdc, identity.agentId, identity.provisioningStatus);
```

`register()` requires the payer's wallet address, either in the request or from the wallet client.
The connected signer must match that payer; use `ownerAddress` for a different designated NFT
owner. When the API returns an x402 challenge, the SDK signs and submits the exact challenged
request once on Base mainnet. It does not automatically replay a paid request after an unknown
outcome.

## Asynchronous registration

New in 0.9.0: submission, status, waiting, and recovery methods distinguish payment acceptance
from completed registration. SDK 0.8.x and earlier may treat HTTP `202` as a complete
`RegistrationResult`; do not infer readiness from their return types. Upgrade to 0.9.0 or use
the [HTTP status contract](/api-reference/register/) directly.

```ts
import { RegistrationPendingError } from '@agentdomain/sdk';

const controller = new AbortController();
try {
  const submission = await agentDomain.submitRegistration(
    { preferredName: 'research-agent', tld: 'com' },
    { signal: controller.signal },
  );
  const result =
    'status' in submission
      ? await agentDomain.waitForRegistration(submission, {
          timeoutMs: 600_000,
          signal: controller.signal,
        })
      : submission;
  console.log(result.agentId);
} catch (error) {
  if (!(error instanceof RegistrationPendingError)) throw error;
  console.log(error.reason, error.handle);
  // Read status later with the payer wallet. Do not start another paid checkout.
}
```

`register(args, { timeoutMs, signal })` combines submission and waiting. It sends
`Prefer: respond-async`, preserves legacy `200` results, and handles `202` by polling GETs only.
Submission and individual reads default to a 60-second deadline; the wait defaults to ten minutes
after acceptance. The wait timeout does not extend a submission deadline. Polling honors the
server's interval and transient-read `Retry-After` with a five-second minimum and stops when user
action is required.

`getRegistration(id)` returns `RegistrationProgress`; `getRegistrations({ limit, offset })` returns
the payer's paginated list, defaulting to 20 entries with a maximum of 50. These methods never
authorize with an agent API key or payment header.
Wallet clients sign `agentdomain.app api auth <timestampMs>` for `X-Agent-Signature`; the SDK caches
the signature in memory for up to four minutes and refreshes before its five-minute expiry.
Signing rejection and authorization failure stop the waiter, avoiding repeated wallet prompts.
Signature-authenticated registration requests omit cookies so another wallet's SIWE session
cannot override the signer. Status, list, and recovery reads send `expectedPayer` and verify
`X-Authenticated-Wallet` on successful responses before decoding their bodies. The query parameter
does not authenticate the request; it checks the authenticated identity against the intended payer.

For an existing browser SIWE session, construct the client with `registrationAuth: 'session'`.
Without a wallet client, also supply `registrationExpectedPayer` in the constructor or
`expectedPayer` per request. Cookies are included and reads do not prompt the wallet. Unbound
session-only reads fail locally, while a cookie belonging to another payer is rejected by the API.
Use the same host for sign-in and reads.
The payer is the authorized registration reader even when another wallet will own the NFT.

On `completed`, the waiter returns `progress.result`. It never manufactures missing token IDs,
transaction hashes, or metadata. Missing legacy results produce a pending recovery diagnostic.
`RegistrationFailedError` represents a server-confirmed `failed` or `refunded` status;
`RegistrationPendingError` represents timeout, abort, an unknown outcome, or an actionable state.
Neither is an instruction to pay again.
Minimal `202 action_required` responses also raise `RegistrationPendingError` with a reusable
handle, without a second payment attempt.

After a lost submission response, use its error handle with `getRegistration(handle.registrationId)`
when an ID is known, or `recoverRegistration(handle)` when unknown. Recovery performs only
payer-authenticated list/detail reads, matching the exact domain and inclusive submission time
window. It scans at most ten pages of 50 entries (500 total) and refuses multiple matches, no match, or an
incomplete search. Clock skew can prevent matching; no match is not proof that payment failed.
No transport error triggers an automatic payment POST retry.
SDK-generated pending handles also retain `payerAddress`; recovery cannot silently switch to a
different signing wallet. Session-only callers can pass `handle.payerAddress` as `expectedPayer`
when calling a detail read directly.
Known-ID recovery checks the same domain, inclusive time window, and authenticated payer as
unknown-ID discovery. An inconsistent handle is rejected rather than returning another purchase.
When only the registration ID is known, use an authenticated `getRegistration()` call.

HTTP `200` registration results are also schema-projected: required fields must be present,
the returned domain must match the submitted request, and unknown fields are stripped,
including unknown nested snapshot fields. Public snapshot values and items are retained without
repricing or truncation. Invalid responses retain a pending handle and never trigger another payment.

## Upgrading from 0.8.x

Existing `register(args)` calls remain valid, but HTTP `202` now starts authenticated waiting.
Use `submitRegistration()` for acceptance without waiting for asynchronous provisioning, and
handle the structured pending and failed errors above. Registration does not use an agent API key for authentication. Custom
API adapters must implement the documented status contract and expose `X-Authenticated-Wallet`.
Constructor URL validation also applies to clients used only for discovery.

Align/deduplicate viem to the reviewed 2.56.3 version across your client code and SDK dependencies.
An independently pinned 2.55.8 `PublicClient` lacks the required `watchBlockHeaders` member and
can fail TypeScript assignment. Arbitrary mixed-version viem compatibility is not guaranteed;
SDK import paths and ESM-only packaging are unchanged.

The x402 packages are aligned at 2.25.0. The payment helper explicitly disables the new upstream
default $1 cap and recognized-asset allowlist, preserving its earlier payment-selection policy.
It does not impose a new spending budget or independently verify an earlier quote; callers must
authorize the payment terms. Base-mainnet exact v2 signing and existing request-binding checks
remain in place.

## Email and DNS

```ts
await agentDomain.sendEmail(agentId, {
  to: 'operator@example.com',
  subject: 'Status',
  text: 'Agent online.',
  idempotencyKey: crypto.randomUUID(),
});

const records = await agentDomain.listDnsRecords(agentId);
const preview = await agentDomain.previewDnsBatch(agentId, desiredRecords, 'merge');
await agentDomain.applyDnsBatch(agentId, desiredRecords, preview.baseRevision, 'merge');
```

Use [Email API](/api-reference/email/) and [DNS API](/api-reference/dns/) limits when designing
automation.

## Owner-controlled auto-renew

Direct Base writes require the public RenewalVault address and a public ERC-8021 builder code:

```ts
import type { Address } from 'viem';

const agentDomain = new AgentDomain({
  walletClient,
  publicClient,
  renewalVaultAddress: '0xb7b19826a566ebd9e8b50bee986a8da04bbb2c0a' as Address,
  builderCode: 'my_agent_app',
});

const status = await agentDomain.getRenewalStatus(agentId);
if (Number(status.shortfallUsdc) > 0) {
  await agentDomain.fundRenewalVault(agentId, status.shortfallUsdc);
}
await agentDomain.setAutoRenew(agentId, true, { waitForReceipt: true });
```

The wallet client must be the AgentID NFT owner for `setAutoRenew()`. The builder code contains 1
to 32 lowercase letters, numbers, or underscores and is public attribution, not a credential.

## Registry and plans

The SDK also includes registry search, agent lookup, API key management from owner sessions,
service-plan status and purchase, registry visibility, email usage and webhooks, DNS import/export,
and owner-authorized vault withdrawal.

Read the [API error contract](/api-reference/overview/#errors) and handle stable error codes rather
than parsing message text.
