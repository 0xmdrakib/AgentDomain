title: Registration API
description: Quote and register an identity bundle through the public x402-protected API.
---

## Quote

```http
GET /api/v1/agents/quote
```

```text
?preferredName=research-agent&tld=com&registerBasename=false&registerEns=false&years=1
```

The response itemizes the domain, optional onchain names, selected plan, included services, annual
platform fee, and total USDC amount. Quotes can change until payment is accepted, so request a fresh
quote immediately before checkout.

## Register

```http
POST /api/v1/agents/register
```

```json
{
  "wallet": "0x1111111111111111111111111111111111111111",
  "ownerAddress": "0x1111111111111111111111111111111111111111",
  "preferredName": "research-agent",
  "tld": "com",
  "registerBasename": true,
  "basenameLabel": "research-agent-ai",
  "registerEns": false,
  "emailUsername": "agent",
  "premiumPlan": "included",
  "years": 1,
  "autoRenew": false
}
```

New clients should send `Prefer: respond-async`. The first request can return an x402 v2
challenge. Submit the exact challenged request with the signed `PAYMENT-SIGNATURE` header once.
Successful settlement details are returned in `PAYMENT-RESPONSE`. A lost response or uncertain
payment outcome is not permission to submit another payment.

## Fields

| Field              | Required | Notes                                                    |
| ------------------ | -------- | -------------------------------------------------------- |
| `wallet`           | yes      | Wallet authorizing payment                               |
| `ownerAddress`     | no       | Final owner; defaults to `wallet`                        |
| `preferredName`    | yes      | Requested domain label                                   |
| `tld`              | yes      | Supported top-level domain                               |
| `registerBasename` | no       | Defaults to `true` in SDK 0.7.0                          |
| `registerEns`      | no       | Defaults to `false` in SDK 0.7.0                         |
| `emailUsername`    | no       | Primary address local-part; defaults to `agent`          |
| `premiumPlan`      | no       | `included`, `starter`, `pro`, or `enterprise`            |
| `years`            | no       | Initial term from 1 through 10 years                     |
| `autoRenew`        | no       | Records intent; owner still authorizes the vault onchain |

Email, managed DNS, HTTPS, and AgentID NFT orchestration are part of the identity bundle. Optional
onchain names are charged only when selected.

## Acceptance and completion

HTTP `202` means payment was accepted and work is still processing. Its minimum body is:

```json
{
  "registrationId": "11111111-1111-4111-8111-111111111111",
  "status": "processing",
  "statusUrl": "/api/v1/registrations/11111111-1111-4111-8111-111111111111",
  "domain": "research-agent.com",
  "paymentStatus": "settled",
  "pollAfterSeconds": 5
}
```

The response may include the full progress fields below. Keep the handle and poll status using
the payer's authentication. Never treat `202` as a completed `RegistrationResult`.
An existing registration requiring review may instead return `202` with a minimal
`action_required` handle. Keep that handle and read status; this does not authorize another payment.

HTTP `200` on the registration POST retains the existing `RegistrationResult` shape, including
the existing transaction, metadata, and renewal fields. For example:

```json
{
  "registrationId": "registration-reference",
  "agentId": "agent-reference",
  "nftTokenId": 42,
  "domain": "research-agent.com",
  "basename": "research-agent-ai.base.eth",
  "ensName": null,
  "sslStatus": "pending",
  "metadataUri": "ipfs://bafy...",
  "provisioningStatus": "processing"
}
```

Legacy inline requests can still return `202` when unfinished. A legacy `200` result whose
`provisioningStatus` is `processing` is not proof that all services are ready.

## Payer-scoped status reads

```http
GET /api/v1/registrations/{registrationId}
GET /api/v1/registrations?limit=20&offset=0
```

Authenticate using the payer's SIWE session cookie, or:

```text
X-Agent-Signature: <payerAddress>:<timestampMs>:<signature>
Signed message: agentdomain.app api auth <timestampMs>
```

The timestamp is Unix milliseconds. Agent signatures expire after five minutes; clients should
reuse a fresh signature during polling and refresh before expiry. A different designated NFT owner,
agent-scoped API key alone, payment signature, payment identifier, or transaction hash does not
authorize these reads. Missing authentication returns `401`; another payer's registration and an
unknown ID both return `404`. Browser sessions must use the same API host for sign-in and reads.
Both reads accept an optional `expectedPayer` wallet query parameter. The API authenticates first,
then rejects a mismatch with `401`; the query is not authentication or delegation. Successful reads
expose `X-Authenticated-Wallet`. Clients should bind requests to the intended payer and verify this
header, especially when SIWE cookies and a wallet signer could belong to different wallets.

Status GET returns HTTP `200` with `RegistrationProgress`. List GET returns
`{ items: RegistrationProgress[], hasMore: boolean, total: number }`, scoped to the authenticated
payer before pagination. The default page size is 20, with a maximum of 50. These are private,
non-cacheable reads; polling does not start or restart a purchase.

| Field                                   | Contract                                                                                                        |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `registrationId`, `statusUrl`, `domain` | Stable registration handle and requested domain                                                                 |
| `status`                                | `processing`, `completed`, `action_required`, `failed`, `refunded`, `awaiting_payment`                          |
| `agentId`                               | Linked agent ID, or `null`; its presence alone does not mean completion                                         |
| `paymentStatus`                         | `unknown`, `pending`, `settled`, `not_charged`, `refunded`                                                      |
| `stage`                                 | `payment`, `domain`, `dns`, `ssl`, `email`, `basename`, `ens`, `mint`, `finalizing`, `complete`                 |
| `messageCode`                           | Public machine-readable message code, not a raw diagnostic                                                      |
| `startedAt`, `updatedAt`                | ISO timestamps                                                                                                  |
| `completedAt`                           | ISO completion timestamp, or `null`                                                                             |
| `revision`                              | Nonnegative status revision                                                                                     |
| `estimatedDurationSeconds`              | Estimate in seconds, or `null` when unavailable                                                                 |
| `pollAfterSeconds`                      | Suggested polling interval; normally 5 during processing and 30 when action is required                         |
| `completionEventId`                     | Completion event identifier, or `null`; can deduplicate notifications                                           |
| `result`                                | Optional public `RegistrationResult`, populated only on `completed`; may be missing or `null` for older records |

`completed` means the identity and all selected services are ready, including DNS, HTTPS, email,
and selected onchain names. Payment settlement, minting, or an agent ID alone is insufficient.
There is no instant completion guarantee. Stop automatic waiting on `action_required`, `failed`,
`refunded`, or `awaiting_payment` and inspect the state; none automatically authorizes repayment.

## Lost responses and upgrades

If the submission response is lost, authenticate as the payer and read the registration list.
Match the exact domain and submission time interval; do not guess if multiple attempts match.
A missing match does not prove no charge occurred. Keep known registration/payment references
for support, but never use them instead of wallet authentication.

The asynchronous SDK methods documented in the [TypeScript guide](/sdk/typescript/) are currently
unreleased source additions. An already published SDK can mistake `202` for a completed result;
an old TypeScript return type does not make that safe. Integrate this HTTP contract directly or
upgrade to a release containing the new waiter when available. No package version change is
implied by this documentation.
